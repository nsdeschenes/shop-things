# Application monitoring

Settings is available from the header before database setup and during recovery. Database (`/settings/database`) is the default tab. Select Monitoring (`/settings/monitoring`) to enter a Sentry DSN and save. Switching tabs preserves unsaved monitoring edits. A blank DSN disables monitoring. Enabling, disabling, or changing the destination takes effect after quitting and restarting Shop Things. Reloading the window retains the active destination.

Main owns `telemetry.json` in Electron's user-data directory. Its fields are `dsn` and `sampling`, containing error, trace, log, and metric percentages. Writes replace the file atomically with owner-only permissions. `database.json` remains independent. Missing, malformed, or disallowed monitoring settings disable monitoring while the application remains usable. Settings shows the saved values and whether a restart is required. The startup DSN and sampling stay immutable for the process lifetime. Authorized `telemetry.status` also returns that active configuration to initialize the renderer. It never travels in command-line arguments.

Error, trace, log, and metric sampling accept percentages from 0 to 100, including decimals. All default to 100%, preserving existing behavior and older DSN-only files. Files with only error and trace percentages retain those values and default logs and metrics to 100%. Saving a sampling-only change also requires quitting and restarting. Both SDKs convert error and trace percentages to their `sampleRate` and `tracesSampleRate` options. Logs and metrics are sampled independently in their send hooks after the privacy allowlist is checked. At 0%, that signal is dropped; at 100%, all eligible signals are sent. Metric sampling retains individual measurements; counts are not automatically scaled to estimate the dropped measurements. Sampling does not connect main and renderer traces.

The native adapter uses `@sentry/electron` 8.1.0 APIs, its Electron network transport, and its uncaught-exception integration. The `@sentry/effect/server` 11.4.0 initializer delegates to the Node SDK and initializes the client synchronously before app readiness with Effect SDK metadata. Electron's full initializer installs additional SDK IPC outside the application's document authorization, so it is not used. The Electron transport waits for app readiness before sending and uses an in-memory session; offline persistence is not enabled. The renderer uses `@sentry/react` 11.4.0 with direct browser ingestion. The sandboxed preload contains only the application bridge. The packaged renderer restricts `connect-src` to the active DSN origin. Development also allows its own origin so StyleX can load route styles from Vite. Self-hosted ingestion must accept CORS requests from the packaged `file://` renderer. Production requires HTTPS for remote destinations. Production allows HTTP only when the URL-normalized hostname is exactly `localhost`, `127.0.0.1`, or `[::1]`. Development also allows remote HTTP. Loading persisted settings and saving both enforce this policy without contacting the destination. Disallowed persisted destinations disable monitoring and produce a generic load error. Rejected saves leave the file and active configuration unchanged. A blank DSN always disables monitoring after restarting.

Both processes use the same Sentry environment: `development` when Electron is unpackaged and `production` in packaged releases. Main supplies this immutable label through authorized `telemetry.status`. Errors retain `environment`; streamed spans, logs, and metrics retain `sentry.environment`, including after final scope filtering. Shell variables and scope attributes cannot replace this app-owned label. The environment is not persisted or editable, and both labels use the configured DSN. Sentry creates an environment when it receives labeled telemetry.

## Signals

Each authorized action produces a named main span. Database operations and import, export, restore, startup, reload, and protected shutdown produce phase spans. Renderer client calls produce elapsed action spans. Sentry's TanStack Router integration automatically instruments page loads and navigation with route templates. Browser tracing collects real CLS, LCP, INP, FP, FCP, TTFB, resource timing, and browser navigation timing. Chromium supplies long animation frames where supported, otherwise long tasks. These diagnostics require an active span when the browser reports the entry. Browser diagnostics use trace sampling, including Web Vitals. Native soft-navigation and bfcache behavior remains enabled where supported. Fetch and XHR tracing and HTTP timing instrumentation remain disabled because application calls use IPC. Emission hooks remove raw URLs and route parameters added by the integration. Main and renderer traces are independent. There is no IPC trace-parent propagation.

`application.action.count` counts completion outcomes. `application.action.duration` records milliseconds. Both include static action, outcome, process, and an optional contract error code. `Application action database.status completed` is an example completion log. Main emits completion logs through `Effect.logInfo` and the official `SentryEffectLogger`; its send hook restores the static message template and known action parameter. Renderer uses `Sentry.logger.fmt` with the same template. The privacy filters retain `sentry.message.template` and its single action parameter for grouping, together with the same bounded attributes; unknown templates, action names, and extra parameters are excluded. Known cancellation, validation, busy, stale, and unavailable outcomes produce these signals without exception events.

Main captures original unexpected exceptions through the existing service and IPC error handlers, plus uncaught failures and abnormal renderer load or lifecycle failures. Effect phase spans use `SentryEffectTracer` under the active native action and preserve native child span ancestry across asynchronous work. The tracer marks failed phases without capturing exceptions; handled typed failures and interruptions stay with existing error boundaries. Renderer uses native GlobalHandlers, Dedupe, LinkedErrors, and the SDK React error handler to capture React root, unexpected router, global error, unhandled rejection, and client-caught transport faults. Main also uses Dedupe and LinkedErrors alongside its native exception and rejection integrations. The SDK owns duplicate suppression and exception construction. Expected customer request errors and React Query cancellation are excluded at the error send boundary. Native safe error responses do not create duplicate renderer exceptions. Reporting failures cannot change client results. Protected close waits for a bounded main flush. BrowserTracing finishes active navigation and flushes the renderer on pagehide.

Effect programs receive the official tracer and a filtered Effect logger layer. The logger accepts only approved static messages before the SDK can serialize them, carries validated annotations, and blocks annotations from supplying customer attributes absent from the action context. Each action or phase owns an isolated Effect metric registry. Scope finalization exports approved counters and single-observation action duration histograms while their parent span is still active, including failed and interrupted phases. Action completion uses Effect finalizers and a monotonic Effect clock. Registries are released with each scope, so customer dimensions and counter state do not accumulate across actions. The installed SDK metric layer uses a global registry, exports histogram summaries every ten seconds, and has no final export; this app uses a scoped exporter to preserve per-action duration distributions, trace linkage, independent sampling, and bounded shutdown flushing. Other metric names, types, and multi-observation duration histograms are excluded by the application signal contract. No automatic Effect error reporter is installed.

## Privacy

Collection defaults and integrations are explicitly restricted. Application attributes are validated where actions enter telemetry. SDK events retain native names, fingerprints, transactions, exception types, mechanisms, linked exception relationships, source context, stack frame functions and positions, contexts, and future metadata. A shared error scrubber replaces exception messages and excludes frame variables and user, request, and message payloads. Code locations retain directories, extensions, and chunk hashes. The scrubber redacts usernames under `/home`, `/Users`, and Windows `Users` directories, including file URLs, and removes URL queries and fragments. Other source paths remain intact. Error tags and extras retain harmless SDK diagnostics after targeted filtering. Trusted capture-hint action attributes replace scoped customer values. Customer names, addresses, cities, provinces, postal codes, phone numbers, email addresses, comments, internal row IDs, search values, whole action arguments or results, query keys, DSNs, selected paths, and raw SQL are excluded. Settings discloses that customer number, stock, balances, and donation flag supplied when creating or updating a customer may be reported. The permitted customer attributes are `customerNumber`, `stock`, `previousBalance`, `balance`, and `donate`, each validated against its domain type. Validated create and update arguments supply these attributes to action spans, logs, metrics, and unexpected failures in both processes. Error events retain them as searchable tags and extra context. Balances use two decimal places. Create has no customer number argument; updates include only supplied changes. Main carries these validated arguments through asynchronous action context into nested database and file spans, logs, metrics, and captured errors. Concurrent actions have separate context; unrelated actions and renderer navigation supply no customer attributes. SDK scopes cannot supply omitted customer attributes. Customer records are never serialized. A final envelope scrub removes known private attributes from logs and metrics after SDK scope attributes are merged, while retaining native SDK diagnostic attributes.

Browser spans retain native names, operations, origins, measurements, timestamps, status, parent linkage, route-template IDs, and future SDK metadata. A targeted scrub removes raw URLs, route parameters, DOM selectors and element IDs, script invokers that can contain DOM attribution, personal customer fields, and raw SQL. Names copied from DOM attribution are redacted. Component names, code locations, source function names, URL scheme and domain, server addresses, static database identities, and native user agents remain. URL names retain their path after query and fragment removal. Manual telemetry data must be validated at its source. Harmless unknown SDK attributes remain; the final merged payload cannot distinguish an unknown SDK field from an arbitrary manual scope field.

Individual Turso executions produce inactive `database.query` spans with `db.query` operation under the active database phase. Database opening injects a client-local, SDK-free passive observer before recognition and migrations. Direct `all`, `get`, `run`, and `exec` calls and explicit prepared statement `all`, `get`, and `run` executions each produce one span. Preparing a statement produces none. Fluent statement modes preserve observation; native BEGIN, COMMIT, ROLLBACK and nested savepoint controls each produce their own execution span. Disabled monitoring omits the observer. The database owns execution and timing; observer and SDK failures cannot retry a query or replace its result or error.

Query attributes include SQLite system, finite operation and method, completion outcome, and monotonic driver-call duration in milliseconds. SQL display and table attribution are optional. A bounded tokenizer and supported-shape parser reconstruct display solely from trusted keywords, operators and source-schema vocabulary. Literal strings, blobs, numbers and parameter names become `?`; comments disappear. Unknown identifiers, statements rejected by the supported-shape parser, and input/token/depth/output limits omit both SQL and table. The parser validates display shapes rather than complete SQLite syntax. `VACUUM INTO ?` never reveals the backup destination. Supported displays include application SELECT/subqueries, INSERT/UPDATE/DELETE/RETURNING, recognition PRAGMAs, transaction controls and VACUUM. DDL, triggers, CTEs and other complex migration forms currently keep operation and timing only. Runtime schema results never extend the vocabulary.

Only app-owned query spans can carry SQL display metadata. Main span serialization and final streamed envelopes rebuild query attributes from owned descriptors and execution-time action context. SDK scopes cannot fabricate missing SQL, table, method, operation, or approved customer values on main spans. The targeted log, metric and error scrubbers still reject SQL text and parameters. Static database system, operation, collection, and method attributes remain available outside owned query spans. Query failures mark only the query span as failed; they do not capture an exception. Existing action error handling remains responsible for unexpected application failures. Driver-call duration includes queue, compilation and I/O wait, rather than engine CPU time. Multi-statement `exec` has one observed execution window. Unused iterator, batch and `transactionAsync` APIs and engine-internal trigger bodies are outside coverage. The audited native transaction receiver must be rechecked on driver upgrades.

Native dumps, screenshots, replay, console and DOM breadcrumbs, automatic network and database instrumentation, local variables, user information, cookies, headers, request bodies, and query strings are disabled. Preview never initializes either SDK and never persists monitoring configuration. No source-map upload or external credentials are required.

Inherited Sentry environment trace and baggage are ignored. Span streaming is explicit, and Spotlight is disabled, so environment overrides cannot bypass span sanitization or add an ingestion destination. Log parent span IDs are retained only when they are valid 16-character hexadecimal identifiers.

## Verification

Run the package tests, typecheck, production build, lint, and formatting checks. Then run the production Electron collector test:

```sh
pnpm build
node acceptance/buildHarness.mjs
pnpm exec playwright test --config acceptance/playwright.config.ts monitoringLifecycle.spec.ts monitoringSettings.spec.ts productionTelemetry.spec.ts browserDiagnostics.spec.ts
```

The collector listens on localhost and inspects real event, streamed-span, log, and metric envelopes from both processes. It verifies cold-restart activation, disabled delivery, private payloads, both environment labels on every signal type, and Settings during held database startup. A focused browser scenario produces real visible content, layout shift, and a slow native click to verify numeric LCP, CLS, INP, paint, resource, and long-frame diagnostics. Native error scenarios verify SDK metadata, linked causes, React and global mechanisms, same-object duplicate suppression, distinct errors, expected-error exclusion, and privacy after scope poisoning. Query assertions cover native and prepared execution counts, real constraint and unknown-column failures, scrubbed backup paths, parent linkage, timing, approved argument propagation, prepared reuse across actions, scope poisoning and overlapping BUSY requests. The production-label scenario sets `app.isPackaged` in the test launcher; it exercises built application code without building an installer. Linux containers may need Xvfb and runtime libraries. Set `SHOP_THINGS_ACCEPTANCE_NO_SANDBOX=true` only in a test container whose Electron sandbox helper cannot be used. The production BrowserWindow still sets `sandbox: true`.
