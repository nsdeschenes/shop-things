# Application monitoring

Settings is available from the header before database setup and during recovery. Database (`/settings/database`) is the default tab. Select Monitoring (`/settings/monitoring`) to enter a Sentry DSN and save. Switching tabs preserves unsaved monitoring edits. A blank DSN disables monitoring. Enabling, disabling, or changing the destination takes effect after quitting and restarting Shop Things. Reloading the window retains the active destination.

Main owns `telemetry.json` in Electron's user-data directory. Its fields are `dsn` and `sampling`, containing error, trace, log, and metric percentages. Writes replace the file atomically with owner-only permissions. `database.json` remains independent. Missing or malformed monitoring settings disable monitoring while the application remains usable. Settings shows the saved values and whether a restart is required. The startup DSN and sampling stay immutable for the process lifetime. Authorized `telemetry.status` also returns that active configuration to initialize the renderer. It never travels in command-line arguments.

Error, trace, log, and metric sampling accept percentages from 0 to 100, including decimals. All default to 100%, preserving existing behavior and older DSN-only files. Files with only error and trace percentages retain those values and default logs and metrics to 100%. Saving a sampling-only change also requires quitting and restarting. Both SDKs convert error and trace percentages to their `sampleRate` and `tracesSampleRate` options. Logs and metrics are sampled independently in their send hooks after the privacy allowlist is checked. At 0%, that signal is dropped; at 100%, all eligible signals are sent. Metric sampling retains individual measurements; counts are not automatically scaled to estimate the dropped measurements. Sampling does not connect main and renderer traces.

The native adapter uses `@sentry/electron` 8.1.0 APIs, its Electron network transport, and its uncaught-exception integration. A small `@sentry/node` 11.4.0 bootstrap initializes the client synchronously before app readiness. Electron's full initializer installs additional SDK IPC outside the application's document authorization, so it is not used. The Electron transport waits for app readiness before sending and uses an in-memory session; offline persistence is not enabled. The renderer uses `@sentry/react` 11.4.0 with direct browser ingestion. The sandboxed preload contains only the application bridge. The packaged renderer restricts `connect-src` to the active DSN origin. Development also allows its own origin so StyleX can load route styles from Vite. Self-hosted ingestion must accept CORS requests from the packaged `file://` renderer. HTTP and HTTPS DSNs are supported. Saving validates the DSN format without contacting its destination.

Both processes use the same Sentry environment: `development` when Electron is unpackaged and `production` in packaged releases. Main supplies this immutable label through authorized `telemetry.status`. Errors retain `environment`; streamed spans, logs, and metrics retain `sentry.environment`, including after final scope filtering. Shell variables and scope attributes cannot replace this app-owned label. The environment is not persisted or editable, and both labels use the configured DSN. Sentry creates an environment when it receives labeled telemetry.

## Signals

Each authorized action produces a named main span. Database operations and import, export, restore, startup, reload, and protected shutdown produce phase spans. Renderer client calls produce elapsed action spans. Sentry's TanStack Router integration automatically instruments page loads and navigation with route templates. Its network tracing, long-task tracking, and Core Web Vitals are disabled; incidental browser and resource spans are excluded. Emission hooks remove URLs and route parameters added by the integration. Main and renderer traces are independent. There is no IPC trace-parent propagation.

`application.action.count` counts completion outcomes. `application.action.duration` records milliseconds. Both include static action, outcome, process, and an optional contract error code. `Application action database.status completed` is an example completion log. Both processes use `Sentry.logger.fmt` with a static template and a known action name. The privacy filters retain `sentry.message.template` and its single action parameter for grouping, together with the same bounded attributes; unknown templates, action names, and extra parameters are excluded. Known cancellation, validation, busy, stale, and unavailable outcomes produce these signals without exception events.

Main captures original unexpected exceptions through the existing service and IPC error handlers, plus uncaught failures and abnormal renderer load or lifecycle failures. Renderer captures React root, unexpected router, global error, unhandled rejection, and client-caught transport faults. Native safe error responses do not create duplicate renderer exceptions. Reporting failures cannot change client results. Protected close waits for a bounded main flush. Renderer pagehide requests a bounded flush without blocking the interface.

## Privacy

Collection defaults and integrations are explicitly restricted. Emission hooks retain fixed operation names, outcomes, error codes, process, timing, exception types, and sanitized application-relative stack locations. Validated trace and span IDs link errors within their owning process. Exception messages are replaced. Customer names, addresses, cities, provinces, postal codes, phone numbers, email addresses, comments, internal row IDs, search values, whole action arguments or results, query keys, DSNs, selected paths, SQL, and source context are excluded. The only permitted customer attributes are `customerNumber`, `stock`, `previousBalance`, `balance`, and `donate`, each validated against its domain type. Validated create and update arguments supply these attributes to action spans, logs, metrics, and unexpected failures during those calls in both processes. Error events retain them as searchable tags and extra context. Balances use two decimal places. Create has no customer number argument; updates include only supplied changes. Other actions supply no customer attributes. SDK scopes cannot supply omitted customer attributes. Customer records are never serialized. A final envelope filter applies the same allowlist to logs and metrics after SDK scope attributes are merged, removing personal fields and arbitrary attribute metadata.

Native dumps, screenshots, replay, console and DOM breadcrumbs, automatic network and database instrumentation, local variables, user information, cookies, headers, request bodies, and query strings are disabled. Preview never initializes either SDK and never persists monitoring configuration. No source-map upload or external credentials are required.

Inherited Sentry environment trace and baggage are ignored. Span streaming is explicit, and Spotlight is disabled, so environment overrides cannot bypass span sanitization or add an ingestion destination. Log parent span IDs are retained only when they are valid 16-character hexadecimal identifiers.

## Verification

Run the package tests, typecheck, production build, lint, and formatting checks. Then run the production Electron collector test:

```sh
pnpm build
node acceptance/buildHarness.mjs
pnpm exec playwright test --config acceptance/playwright.config.ts telemetry.spec.ts
```

The collector listens on localhost and inspects real event, streamed-span, log, and metric envelopes from both processes. It verifies cold-restart activation, disabled delivery, private payloads, both environment labels on every signal type, and Settings during held database startup. The production-label scenario sets `app.isPackaged` in the test launcher; it exercises built application code without building an installer. Linux containers may need Xvfb and runtime libraries. Set `SHOP_THINGS_ACCEPTANCE_NO_SANDBOX=true` only in a test container whose Electron sandbox helper cannot be used. The production BrowserWindow still sets `sandbox: true`.
